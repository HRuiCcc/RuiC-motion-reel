# 性能：一帧花在哪，以及换显卡到底能省多少

全部是 2026-09-28 在一台 Windows 机器上量的（RTX 5060 / 驱动 595.71 /
Python 3.13.12 / numpy 2.2.4 / CuPy 14.2）。

**先说结论**：这只引擎的瓶颈**不在数学上，在光栅化上**。把 numpy 换成 GPU
顶多快 1.45 倍；而"算子快 40 倍"这种数**不能拿去许诺整帧快 40 倍**——它只覆盖
一帧的三分之一。

## 一、一帧的实测分布（1920×1080 / ss=2，最重的一场，约 4.2 s 墙钟）

| 部件 | 占比 | GPU 可替？ |
|---|---|---|
| PIL 矢量 / 文字通道（`_Pass`：画图元 + `getbbox` 扫描 + 提交） | **~55%** | ❌ PIL 没有 GPU 后端 |
| numpy 后期（commit 降采样、叠印、halation、片门微抖、颗粒、tonemap） | **~33%** | ✅ |
| 点云 3D（`three.render` 排序散射） | ~8% | ✅（但省不下多少） |
| 合成器 DSP | 只在开头跑一次，1.1 s | — |

## 二、算子级有多快，整帧就有多快吗（`scripts/perf_probe.py`）

逐算子 CPU vs CuPy，**按引擎真实的数组尺寸**量：

| 算子 | CPU ms | GPU ms | 倍 |
|---|---|---|---|
| commit 降采样，色彩层 2160×3840 | 201 | 0.7 | 271× |
| vignette（mgrid + sqrt + pow） | 263 | 14.6 | 18× |
| 环境光带（gauss：mgrid + exp） | 242 | 3.5 | 69× |
| 银盐颗粒（rng + 团块 blur + 混合） | 161 | 2.6 | 63× |
| halation 三阶 blur + 上采样叠加 | 227 | 6.4 | 35× |
| 片门微抖，4 tap × 2 缓冲 | 114 | 3.2 | 35× |
| ink 乘算叠印 ×3 | 45 | 0.3 | 133× |
| **合计（每帧 numpy 侧）** | **1292** | **32** | **40×** |

（**绝对值随机器负载浮动**：同一台机上隔一会儿复跑，这张表的总计在 1.3~3.2 秒之间跳过，
看**比例**和**量级**就好，别当基准常数。）

**但这 1292 ms 只占整帧 4.2 s 的三分之一** ⇒ **整帧 4.2 s → 约 2.9 s ≈ 1.45×**。
每帧还有约 18 ms 的 host↔device 传输，可忽略。

**要几倍，就得把 2× 超采样的矢量/文字光栅化搬到 GPU**（moderngl / taichi 一类），
那是重写引擎，不是加开关。

> **量的时候注意**：一定要按**真实数组尺寸**量。引擎的 blur 都在**降采样后的小数组**上
> （`bright[::2, ::2]` 这一级），如果你按全画幅 3840×2160 去量一次 `blur(r=5, passes=3)`，
> 会得到 4.3 秒这种数字，把 GPU 的收益虚高成 72 倍——而引擎永远不干这件事。

## 三、比换显卡便宜的第一步

`mg/core.py` 的 `_Pass` **每画一个图元都做一次全画幅 `getbbox()`**。
在 2× 图层上（2560×1440 或 3840×2160）一次扫描是几毫秒；一帧画上百个 `path`
（水场那一场一帧 336 个）就是上千次扫描，实测占一帧 **~25%**。

把扫描限制在图元自己的包围盒内就行，**画面一个像素都不变**。
先做这个，再谈显卡。

## 四、怎么复量

```bash
py scripts/perf_probe.py            # 逐算子 CPU vs CuPy（没装 CuPy 会直接说）
py scripts/perf_probe.py --full     # 顺带量一遍全画幅 blur，看虚高有多大
```

单帧成本用 `--at` 加 `time` 就行：

```bash
time python3 -m <pkg>.build --at 3:1.60 --ss 2      # 最重的一场
```

## 七、1080p60 的账（2026-09-29 实测）

交付从 720p30 提到 1080p60 是帧数 ×2、像素 ×2.25，但**默认排版空间仍是 720p**，
所以贵的是矢量通道超采样和更大的缓冲，几何与遮罩还在 720p 上算：

| | 720p30 | 1080p60（排版 720p → 交付 1080p） |
|---|---|---|
| 帧数 | 450 | 900 |
| 单帧（本机 Mac，机器空闲） | ~1.3 s | ~1.2~1.7 s |
| 单帧（机器被别的活压满，load 24） | — | ~3.7 s |
| 全片（3 workers） | ~3 min | ~7 min 空闲，满载要 20 min 以上 |

三条要点：

- **排版空间保持 720p 时单帧成本几乎不变**（模板默认就是这条路径）。
  把 `W, H` 提到交付尺寸（丝网印/凸版/拼贴这类细纹理的牌）才会真的 ×2 以上。
- **编码**：1080p60 的 900 帧走 `libx264 -preset slow` 约比 720p30 慢 3~4 倍；
  有 NVIDIA 卡就走 nvenc（模板已用 `ffmpeg -encoders` 探测，没有就静默用 x264）。
- **并行度仍然是一场景一核**（`cpu_count // 3`），别把机器吃满——
  这条是用户原话定的：「并行度不许吃满全机，cpu 爆了」。
